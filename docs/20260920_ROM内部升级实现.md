## 修改内容

播放器新增 `RomUpdateManager.java`，在 `AppUpdateCoordinator.java` 中先检查 ROM，再检查 APK。读取同一 `onlineVodHost:9898`；`romUpdateEnabled` 默认 true，与 `appUpdateEnabled` 独立。旧 ROM 没有控制器时跳过 ROM 流程。下载有长度、SHA-256、空间、取消和互斥检查；签名由固定平台公钥验证，App 不能直接写分区。

`system-integration/hsvj-rom-update` 是原生控制器及构建工具的维护入口。控制器提供 `--status`、`--stage NAME`、`--manifest ID`、`--check ID`、`--arm ID`。`--recover ID` 只接受 Recovery 父进程调用，验证分区表、挂载占用、签名、全包和各分区内容，使用平台 libsparse 展开，再逐分区写入和读回校验。`--verify-bundle DIR/ ID` 是不访问块设备的构建验证入口。

Recovery 新增 `--hsvj_update=<manifest SHA256>` 内部入口；失败保持维护状态，不落入旧厂商自动格式化分支。修正旧 ZIP 安装失败结果被 rkloader 检查结果覆盖的问题。原有外部刷机入口保留。

构建链改为编译配套 Recovery，仍核对参考启动链哈希并保持稳定内核。新增 `ro.hsvj.rom_update.protocol=1` 和 `ro.hsvj.rom.version=<ROM数字版本>`。Recovery 的 `/data` 和 `/huoshan` 均为 ext4。

`status.json` 保存在 `/huoshan/.rom-update`，记录内核 boot_id；同一次启动内的 armed 状态保持等待重启，并锁定暂存入口。只有写入及读回完成、重启后指纹和版本一致，才标记成功。失败和中断的 release_id 不再自动重试；需修复原因并发布新版本。非 A/B 升级不能保证断电回滚，升级期间必须保持供电。

Android 正常启动的 huoshan 挂载项移除 `formattable`，打包校验同时覆盖正常系统与 Recovery，避免挂载异常触发自动格式化。全新空白 huoshan 分区需要单独的工厂初始化；已有文件系统保持原样。

## API 一对一

所有接口使用现有 `{code,message,data}` 响应封装。

| 方法 | 路径 | 调用方 / 内容 |
| --- | --- | --- |
| POST | `/api/v1/rom-updates/check` | 播放器：protocol、product、hardware、current_version_code；仅选择严格更高版本 |
| GET | `/api/v1/rom-updates/files/:id/:resource` | 播放器：resource 仅 manifest.json、manifest.sig、update.img |
| POST | `/api/v1/rom-updates/report` | 播放器：device_id、release_id、version_code、phase、message |
| GET | `/api/v1/rom-updates/releases` | 管理员：候选包和设备结果 |
| PUT | `/api/v1/rom-updates/releases/:id/publication` | 管理员：`{"published":true/false}` |

候选目录为服务器 `config.toml` 同级 `rom/<release_id>/`。`release_id` 是规范 manifest.json 的 SHA-256；目录必须包含 manifest.json、manifest.sig、update.img。在后台“终端设备管理 → ROM 更新”发布前验证签名和镜像完整 SHA-256，再创建 PUBLISHED 标记。撤回删除标记；已下载并进入本地安装的设备不能通过撤回中止。

设备回报记录在服务器 `data/rom-results/<device_id>.json`，后台可查看。它是设备报告，不用于授权下一次升级。

Windows 官方构建入口：`D:\HVIDEO\HSVJ\build_hsvj_rom.ps1 -ReleaseVersion v32 -Jobs 12 -ResumeAndroidBuild`；完成 v32 后使用相同入口构建 v33，复用已完成缓存。首次无构建缓存时省略 `-ResumeAndroidBuild`。

自 2026-09-22 起，唯一正式入口 `D:\HVIDEO\HSVJ\build_hsvj_rom.ps1` 在完整 ROM 编译成功后自动调用现有 `package_rom.py`，生成并验证 `manifest.json`、`manifest.sig`、`update.img` 三件套。签名/镜像/分区校验失败时构建入口报错，不再把单独 `.img` 当作设备升级交付完成。

本地只交付 `D:\HVIDEO\HSVJ\rom-bundles\VNN\` 下的 `update.img`、`manifest.json`、`manifest.sig`；其中 `update.img` 同时就是完整刷机镜像，清单内包含 SHA-256。根目录不再生成独立 ROM、`.sha256` 或 `.bundle.json`。版本、release_id、路径索引保存在 records 的 `ROM_BUNDLE_vNN.json` 和 `LATEST_BUILD.txt`。导入服务器时将三件套放入 `rom/<release_id>/`，记录中的 `server_directory_name` 给出该名称。该改动不自动发布，也不改变服务器 API。

以下为正式入口内部调用的既有签名工具示例，日常构建无需再手动执行：

```sh
python3 -B /mnt/d/CHUANGWEI/system-integration/hsvj-rom-update/package_rom.py \
  --android-root . --image out-hsvj-user/h66_por_full_update/update.img \
  --pack-dir out-hsvj-user/h66_por_full_update --version 33 \
  --output /mnt/d/HVIDEO/HSVJ/rom-bundles
```

该命令不发布、不访问设备，使用构建主机已有平台密钥签名，校验真实 RKFW/RKAF 分区目录、固定 parameter、Recovery 内核、内部入口、依赖库、ext4 挂载，并运行同源码原生完整校验器。将生成的哈希目录放到服务器 rom 目录后，仍需后台手动发布。
