# 2026-09-18 播放器启动目录升级

## 修改范围

- 服务器 `src/services/apk_manifest.rs` 读取 APK 内二进制 XML 中的包名、versionCode、versionName、硬件元数据，不依赖 Android SDK/Java/文件名。
- `player_release_service.rs` 扫描运行配置同级 `app`，按文件大小/修改时间缓存解析和 SHA-256；无效、损坏、缺失型号、不支持的包名、超 300 MiB 文件不发布。相同型号只选最高 versionCode。
- `player_update_handler.rs` 提供检查和按 SHA-256 下载；只开放 APK，不提供目录浏览或任意文件路径。新增文件/替换文件不需重启。两条接口受服务器授权中间件约束，不需后台登录令牌。
- 播放器 `AppUpdateCoordinator` 复用 `config/config.json` 中 `onlineVodHost` 和固定 9898 端口，替换固定云端检查地址；遵守 `appUpdateEnabled`，启动 8 秒后检查，网络失败 30 秒重试，总计最多 5 次。
- 播放器 `AppUpdateManager` 严格解析统一响应，只有 versionCode 更高才下载；限定同一服务器下载路径。安装前在后台线程校验实际 APK 大小、SHA-256、包名、versionCode、硬件元数据及完整签名集合。错误/超时取消下载并保留现有应用。
- 两个硬件构建变体将 `com.hsvj.engine.HARDWARE` 写入 APK；清理旧云端响应别名、未使用的检查周期/跳过版本代码、重复的下载文件名生成逻辑，修复下载弹窗释放状态。
- 便携打包脚本携带 `app` 目录。PAD 无接口变更。

## 一对一 API

`AppUpdateManager.fetchVersionInfo` → `POST /api/v1/player-updates/check` → `player_update_handler::check`。

请求严格接受以下三个字段，未知字段拒绝：

```json
{"current_version_code":2459,"package_name":"com.hsvj.engine","hardware":"hw81"}
```

响应沿用 `{code:0,message:"success",data:{...}}`；data 固定字段为 `has_update`、`version_code`、`version_name`、`package_name`、`hardware`、`download_url`、`sha256`、`file_size`、`force_update`、`release_notes`。有新版时 `force_update=true`，下载地址为服务器相对地址。无合适安装包时 `has_update=false`、版本为 0；同版/旧版返回所找到版本，下载地址和哈希为空。

`AppUpdateManager.downloadApk` → `GET /api/v1/player-updates/files/{sha256}` → `player_update_handler::download`。

成功返回 APK 流和准确的 Content-Length；非法哈希 400，移除/替换后找不到原包返回 404。两接口均 `Cache-Control: no-store`，不添加旧接口别名。下载后再次核对哈希，防止发布目录在检查后被替换造成错误安装。

## 部署

1. 更新服务器程序，保持其 config.toml、数据库、授权和其他资源。
2. 先通过现有后台 ADB 更新或本地安装给播放器安装本次对应硬件的新 APK。
3. 此后把对应硬件、同签名的更高版本 APK 放入 config.toml 同级 app 即可。推荐 `.part` 复制完成后改名 `.apk`。
4. 真机无 root 安装权限时需要系统安装确认。安装沿用原有保留数据安装和恢复播放器机制。
