## 二、技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| **编程语言** | Rust | 高性能、内存安全、零成本抽象 |
| **Web框架** | Axum 0.7 | 基于 Tower 生态，类型安全，支持 WebSocket |
| **数据库** | SQLite (WAL) | 嵌入式，无需额外部署，WAL模式支持并发读 |
| **反向代理** | Nginx | 静态文件高性能分发，限流，WebSocket代理 |
| **异步运行时** | Tokio | Rust 标准异步运行时 |
| **认证** | JWT + API Key/Secret | 无状态认证，适合分布式 |
| **实时通信** | WebSocket | 低延迟双向通信，房间状态同步 |

## 四、核心模块详细设计

### 4.1 数据库设计 (8张核心表)

| 表名 | 用途 | 核心字段 |
|------|------|----------|
| `artists` | 歌星库 | id, name, pinyin, initial, gender, region, song_count |
| `songs` | 歌曲库 | id, title, pinyin, artist_id, language, genre, file_path, cloud_file_id, play_count |
| `rooms` | 房间 | id, name, terminal_id, status, current_song_id, volume |
| `room_queue` | 点歌队列 | id, room_id, song_id, position, status, is_priority |
| `terminals` | 终端设备 | id, ip_address, mac_address, online_status, last_heartbeat |
| `api_clients` | API客户端 | id, client_key, client_secret, permissions, rate_limit |
| `sync_tasks` | 同步任务 | id, task_type, target_id, status, downloaded_size |
| `operation_logs` | 操作日志 | id, action, target_type, detail |

### 4.2 歌曲/歌星管理

**功能**: 完整的 CRUD + 高级搜索

- **搜索方式**: 歌名、拼音首字母、歌星名、语种、分类
- **拼音索引**: 每条记录存储 pinyin(全拼) 和 initial(首字母)
- **冗余优化**: 歌曲表冗余存储 artist_name，避免 JOIN 查询
- **歌星关联**: 歌曲创建/删除自动更新歌星的 song_count

```
GET    /api/v1/songs?keyword=月亮&language=国语&page=1&page_size=20
POST   /api/v1/songs          { title, pinyin, artist_id, ... }
PUT    /api/v1/songs/:id      { title, status, ... }
DELETE /api/v1/songs/:id
```

### 4.3 房间状态管理

**设计理念**: 房间 = 终端 + 点歌队列 + 播放状态

```
房间状态机:
  空闲(0) ──[终端上线]──> 使用中(1)
  使用中(1) ──[终端离线]──> 空闲(0)
  任意状态 ──[维护]──> 维护中(2)
```

**点歌队列**:
- 顺序播放，支持插播(is_priority)
- 队列项状态: 等待(0) → 播放中(1) → 已播放(2) / 已跳过(3)
- 操作: 点歌、切歌、置顶、清空

**房间控制命令** (通过 WebSocket 下发):
- Play / Pause / NextSong / SkipSong / Replay
- SetVolume / SetMic / ClearQueue

```
POST /api/v1/rooms/:id/queue      点歌
POST /api/v1/rooms/:id/next       切歌
POST /api/v1/rooms/:id/command    控制命令
```

### 4.4 终端设备管理

**自动发现流程**:
```
定时任务 → UDP v2 广播查询（随机 challenge）
  → HSVJ Player 原样回传 challenge 和固定身份字段
  → 服务端校验来源 IP、device_role、app_id、协议版本和 challenge
  → 新播放器自动注册并创建房间；已注册播放器更新在线状态
```

**心跳机制**:
- HSVJ Player 周期发送带 v2 播放器身份字段的 UDP Beacon。
- 服务端只接收播放器 Beacon，不广播服务端 Beacon，也不提供公开 HTTP 心跳接口。
- 普通主机、其他 HVideo Server 和仅开放业务端口的设备不会被注册。

**管理端操作**:
- `POST /api/v1/terminals/discover`：广播 challenge-response 扫描。
- `POST /api/v1/terminals/register`：仅提交 `terminalIp`，由服务端单播握手验证。

### 4.5 云端入库与文件下载

**当前边界**: 服务器当前只实现已有云端映射歌曲的文件下载，不包含“从云端拉取歌曲元数据并写入业务库”的接口。调用导入前，业务库 `songs` 必须已存在目标歌曲，且 `cloudFileId` 非空。

**流程**:
```
1. GET /api/v1/cloud/status 检查真实云端配置、HTTP 可达性和可导入歌曲数
2. POST /api/v1/cloud/import 校验 songs.id 与 songs.cloudFileId
3. 创建或复用 sync_tasks 下载任务
4. 异步流式下载到 .part，支持 Range 断点续传与文件大小校验
5. 原子重命名后，在同一事务中更新 songs.filePath、songs.fileSize 与任务完成状态
6. 下载失败 → 记录 errorMessage 与 retryCount，仅失败/待处理任务允许重试
```

**批量入库（唯一 camelCase 契约）**:
```
POST /api/v1/cloud/import  { "songIds": ["id1", "id2", ...] }
```

**状态与任务监控**:
```
GET /api/v1/cloud/status
GET /api/v1/cloud/tasks?status=1&page=1&pageSize=20
```

### 4.6 API 注册管理

**认证流程**:
```
1. 管理员创建 API 客户端 → 获得 client_key + client_secret (仅显示一次)
2. 客户端用 key/secret 换取 JWT Token
3. 后续请求携带 Bearer Token
4. 中间件验证 Token → 提取权限
```

**权限体系**:
- `read`: 读取歌曲、歌星、房间等数据
- `write`: 创建、修改数据
- `admin`: 管理终端、API客户端、系统设置
- `download`: 触发云端下载任务

**限流**: 每个 API 客户端可配置独立的 rate_limit (每分钟请求数)

### 4.7 WebSocket 实时通信

**连接管理**:
```
客户端连接: ws://server/ws/{terminal_id}
加入房间:   { type: "join_room", room_id: "xxx" }
```

**消息类型**:
| type | 方向 | 说明 |
|------|------|------|
| `room_update` | 服务端→客户端 | 房间状态变更 |
| `queue_update` | 服务端→客户端 | 点歌队列变更 |
| `command` | 服务端→客户端 | 播放控制命令 |
| `terminal_status` | 服务端→客户端 | 终端状态变更 |
| `join_room` | 客户端→服务端 | 加入房间频道 |
| `heartbeat` | 双向 | 连接保活 |

**消息路由**: 按 room_id 投递，空 room_id 为全局广播

## 六、Nginx 架构职责

```
Nginx (前端入口 :80)
├── /storage/*       → 直接提供歌曲/MV文件 (sendfile, 断点续传)
├── /static/*        → 前端静态资源 (长缓存)
├── /ws/*            → WebSocket 代理 → Axum :3000
├── /api/*           → API 代理 → Axum :3000 (限流: 10r/s)
└── /                → 前端 SPA (try_files)
```

**核心优化**:
- 歌曲/MV 大文件由 Nginx 直接分发，不经过 Rust 进程
- sendfile + 范围请求 = 高性能文件下载
- gzip 压缩 JSON 响应
- 连接池 keepalive 复用

## 七、性能设计要点

1. **SQLite WAL 模式**: 支持并发读，写操作序列化但不阻塞读
2. **拼音索引**: 通过 pinyin/initial 字段 + B-Tree 索引实现快速搜索
3. **冗余字段**: 避免 JOIN，单表查询
4. **Nginx 静态分发**: 大文件不经过应用层
5. **异步下载**: 云端文件下载在后台任务中执行，不阻塞 API
6. **WebSocket 广播**: 基于 broadcast channel，O(1) 投递
7. **连接池**: SQLite 连接池 + Nginx keepalive
